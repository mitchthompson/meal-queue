# Front-End UI Audit - 2026-06-11

Detailed audit of the user interface: layout, responsiveness, accessibility,
and interaction flows. Conducted on `main` (commit `f472ba3`) by reading every
route component and the full stylesheet, plus a visual pass of the
unauthenticated screens in a live dev server at desktop (1280px) and iPhone
(375px) viewports.

## What Is Working Well

- Coherent design system in `app/globals.css`: CSS custom properties, a warm
  consistent palette, uniform radii and spacing.
- `:focus-visible` outlines on all interactive elements.
- Inputs inherit 16px body font, preventing iOS zoom-on-focus.
- The mobile tab bar respects `env(safe-area-inset-bottom)` and its icon-only
  tabs carry `aria-label`s.
- The plan grid's mobile collapse into per-day cards is effective.
- The recipe detail page has a sticky overview panel on desktop and a useful
  step-by-step focus mode.

## Findings

### High-impact UX friction

1. **Feedback messages render far from the action.** Save and error messages
   are appended at the bottom of large panels (for example
   `app/plans/page.tsx` and `app/recipes/page.tsx`). On mobile they are often
   off-screen after a save. No `aria-live`, so screen readers never announce
   them; stale messages persist until the next action. This also limits
   milestone 2's "useful feedback when a save fails" acceptance criterion.
2. **Tap targets below iOS guidance.** `.text-btn` (`min-height: auto;
   padding: 0`) is used for the most-tapped controls: serving `+`/`-`,
   Remove, Have this, Move back, Check/Uncheck all. The mobile media query
   enlarges other buttons but not `.text-btn`.
3. **"Edit recipe" on mobile appears to do nothing.** The editor opens below
   the recipe list in the stacked layout with no scroll-into-view.
4. **Plans page order buries the main content.** Create-plan form, then the
   plans list, then the week grid; the daily-use grid needs two panels of
   scrolling on every visit.
5. **Loading flicker on every navigation.** Each tab switch remounts
   `AuthGate` (a visible "Loading session..." flash, confirmed in the visual
   pass) and refetches all data with bare "Loading..." text. No data is kept
   between pages and there are no skeleton states.

### Auth flow gaps

6. If Supabase email confirmation is enabled, sign-up shows no feedback at
   all (no session is returned and nothing renders a message). There is no
   password-reset path.

### Accessibility

7. No `aria-live` status regions (overlaps finding 1).
8. Every page shares the title "Meal Queue"; no per-page titles.
9. Most pages have no `h1` and start their heading hierarchy at `h2`/`h3`.
10. Serving `+`/`-` buttons have no accessible labels.
11. The quick-add list does not visually indicate which match `Enter` picks.

### Polish and structural notes

12. No `apple-touch-icon`, `theme-color`, or web-app manifest despite iPhone
    Safari being a primary target.
13. Mobile Lunch/Dinner labels are injected with `nth-child` CSS `::before`,
    coupling the stylesheet to markup child order.
14. `formatDisplayDate` is duplicated in four files; the lunch/dinner columns
    are ~330 duplicated lines (both already in the component-hardening
    milestone).
15. Nice-to-haves: screen wake-lock during cooking focus mode, richer
    empty states for new users, dark-mode support.

## Decisions Confirmed with the Owner (2026-06-11)

1. **Scope**: three tracks enter the plan as a new milestone - feedback and
   status overhaul, mobile ergonomics, and loading/caching polish. Auth flow
   completion is deferred.
2. **Sequencing**: UI work runs after the reliability core (milestones 2-4)
   and ahead of component hardening.
3. **Accessibility**: folded into the selected tracks (aria-live with
   feedback; button labels and heading structure with ergonomics; per-page
   titles with loading polish) rather than a separate milestone.

The milestone details live in `ROADMAP.md`.
